## 1. 精确计数仍是主要读取来源

近 12 小时 Insights 样本：按 `kind` 计数 72 次，读取 300,744 行，平均每次 4,177 行。线上未删除条目分布为 note 4,176、message 3,604、decision 48、task 44，均属于同一项目。

每次 4,177 行与 note 总量吻合，提示这些调用可能主要在计数 note；绑定参数不在 Insights 中，不能直接确认。现有 `items_live_kind_created` 索引已存在，单纯再加同类索引并不能消除精确计数扫描整个匹配集合的成本。

调用路径审查：

- `src/items.ts:57`：REST 缺省 `include_total=true`。
- `src/items.ts:130`：计数发生在加入游标条件之前，所以后续页显式请求计数时，仍计算整个筛选集合的总数。
- `public/app.js:75`：只有追加加载且有游标时传 `include_total=false`。首次进入、筛选、刷新及经 `loadProject` 重新加载信息列表仍会计数；这是当前界面显示精确总数所需的行为。
- `src/mcp.ts:65`、`llm/openapi.json`：MCP 省略参数时确实转为 false；显式 true 仍计数。

SQL 模板无法识别上述哪条调用路径贡献了 72 次。Insights 的分页样本平均返回条数可由已有字段推算约为 101，而浏览器列表页使用 limit=50，这提示可能还有 limit=100 的其他调用，但不足以确认客户端身份。

建议：同步、批量读取和轮询调用方显式跳过计数；界面若缓存总数，必须同时定义筛选和数据变化后的失效策略，避免显示旧值。保留 REST 现有默认契约。

## 2. 普通时间游标分页存在可复现的额外扫描

`src/items.ts:94` 先加入快照上界 `created_at <= snapshot`，然后在 `src/items.ts:136` 附近加入游标 OR 条件。执行计划虽然显示使用 `items_live_kind_created`，却不能仅凭索引名称判断是否从游标位置开始读取。

在生产 note 数据中，选择按时间倒序第 2,001 条作为游标。该时间戳之前有 2,000 条较新记录，同时间戳仅 1 条。使用实际完整列表 SQL（含角色和接收者查询）对比：

| 变体 | 返回条数 | rows_read | 单次 duration |
| --- | ---: | ---: | ---: |
| 当前快照上界 + 当前 OR 游标条件 | 101 | 2,203 | 8.7128 ms |
| 将列表查询时间上界收紧到游标时间，其余相同 | 101 | 203 | 4.3414 ms |

完整返回 JSON 的 SHA-256 相同：`159524c29e7b365499cd3d38951d44381ab2d8f758dd7ed0d9627da7599ccf81`。样本读取减少约 90.8%；耗时只是单次样本，不能外推稳定延迟或全天节省。

辅助诊断：简化投影时当前 SQL 读取 2,102 行，单纯换成 `(created_at, id) < (?, ?)` 仍是 2,102 行；在收紧原有快照上界后为 102 行。因此本样本的关键是索引扫描采用的时间上界，单纯替换 OR 写法不足以解决问题。

候选实现：仅对按创建时间倒序、有游标的列表查询，令扫描时间上界取 `min(snapshot, cursor.time)`，同时保留原有严格游标条件。该条件由当前分页语义蕴含，无需新索引。原始快照仍应保存在游标中，计数仍使用原始筛选集合，不能随列表上界一起缩小。

此方案尚未实施。需要回归同时间戳、首尾页、筛选组合、项目边界及快照语义；更新时间排序、正序及 ID 排序需分别分析，不能直接套用本结论。

## 3. 全文搜索分页仍需处理候选及排序

近 12 小时 Insights 样本：

| SQL 类别 | 次数 | 读取行数 | 平均耗时 |
| --- | ---: | ---: | ---: |
| 全文搜索后续页 | 26 | 237,240 | 249.93 ms |
| 全文搜索精确计数 | 29 | 113,564 | 177.58 ms |
| 全文搜索无游标列表 | 1 | 15,924 | 380.38 ms |

生产 `EXPLAIN QUERY PLAN` 确认：

1. `SCAN items_search VIRTUAL TABLE INDEX 0:M2`，先从 FTS 候选开始。
2. `SEARCH i USING INTEGER PRIMARY KEY (rowid=?)`，再查条目。
3. `USE TEMP B-TREE FOR ORDER BY`，按创建时间排序需要临时排序。

查询已经使用 FTS，并非完全没走索引。现有 FTS-first 查询无法直接利用普通 items 时间索引输出全局时间顺序。`LIMIT 101` 不等于最多处理 101 个候选；每页仍可能重复筛选大量 FTS 命中项。查询还执行 `instr(lower(title/content), ...)`，正文校验增加工作量，但本次未逐项量化其耗时。

建议优先关闭无展示需求的搜索精确计数；随后用宽匹配、窄匹配和不同深度分页比较 FTS-first 与按时间扫描/候选分阶段查询。不能直接删除 CROSS JOIN，也不能直接去掉子串校验：前者可能退回项目级扫描，后者可能改变现有匹配语义。普通时间分页的候选修改本身不会消除 FTS-first 的临时排序。
